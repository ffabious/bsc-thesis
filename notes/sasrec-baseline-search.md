# Улучшение обычного encoder baseline

9 ноября 2026. Пользователь разрешил автономно проверять гипотезы и обучать варианты локально. Цель — устойчивый одиночный SASRec-style encoder с историей 50 и полным пересчётом user representation при каждом предсказании. Текущий цикл ограничен пилотом 256; перенос на более крупную когорту — отдельная стадия.

## Фиксированный протокол

Не меняются данные, OOT, target, полный каталог, strict-past prefixes, supervision последней позиции, batch 256, Adam 0.001 / betas (0.9, 0.98), clipping 5 и patience 2 без лимита эпох. Сэмплирование uniform с исключением текущего positive, с возвращением. Вычисления последовательные на локальном MPS FP32, CPU fallback выключен.

Главный критерий — полная model_valid NDCG@10; дополнительно Recall@100, user-macro метрики, repeat / other-in-window / outside-window сегменты и время/память. Для выбора нового quality baseline требуется выигрыш NDCG и Recall не ниже 98% исходного уровня. Это правило отбора рецепта; checkpoint внутри каждого запуска выбирается прежним NDCG-only правилом. Старые seed-42 checkpoint/ranks переиспользуются.

## Порядок и условия продолжения

1. Завершить запрошенный контроль dim 50 / head 1 с прежним BCE-рецептом. От исходного успешного dim 64 / heads 2 меняются только эти две настройки. Его единственная test-оценка выполняет уже согласованное сравнение; дальнейшие решения принимаются по validation.
2. На исходной архитектуре dim 64 / heads 2 изменить только dropout 0.2 → 0.0. Гипотеза: регуляризация может ограничивать выучивание локальных переходов и повторов; ухудшение будет свидетельством пользы прежнего dropout в данном контроле.
3. На той же исходной архитектуре изменить только objective: BCE → cross-entropy по одному positive и 16 тем же uniform negatives. Гипотеза: относительное ранжирование помогает лучше независимой бинарной классификации. Это sampled CE, а не полный CE по каталогу; температура и дополнительные проекции не вводятся. Число/распределение negatives сохраняются.
4. По наблюдениям выбрать не более одного следующего контроля с одним изменением: например, увеличить число negatives у наиболее перспективного objective, если ограничивает покрытие каталога. Гипотеза и конфиг фиксируются до запуска. Если первые проверки не дают основания для продолжения, этот этап пропускается.
5. Для наиболее перспективного рецепта и исходного контроля выполнить парный повтор с seed 43, если рецепт новый. Если победителем остаётся исходный, достаточно его повторного обучения. Проверяется знак и размер validation-выигрыша, а не выбирается удачный seed. При явной неустойчивости новый рецепт не объявляется улучшением.
6. Зафиксировать итоговый рецепт и checkpoint hashes до test. Оценить на test только исходный, запрошенный dim 50 и итоговый рецепт/его повтор; промежуточные кандидаты отбираются по validation. Новые настройки после test в этом цикле не выбираются. Сохранить все training logs/конфиги/отрицательные результаты и сводку влияния факторов.

## Ограничения

Один пилот и два seed не устанавливают потолок качества или переносимость на 1k/всех пользователей. Test уже использовался в прошлых исследованиях; даже сохранённый holdout не является новым независимым benchmark. Парные user-bootstrap интервалы характеризуют фиксированные модели, а не весь процесс поиска. Незначительные различия качества не оправдывают рост стоимости; такой вариант сохраняется как диагностический.

Для objective-проверки используются уже изученные [SCE, §2.2](https://arxiv.org/html/2409.18721v2#S2.SS2) и [заметка о loss/sampling](sasrec-scaling-literature.md); ожидаемый эффект на нашем пилоте остаётся гипотезой. Переписывать архитектуру, split или sampler для этих сравнений не требуется.
