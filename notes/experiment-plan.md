## Отдельная ветка: KV reuse

Сразу после reference implementation проверить на маленьких примерах append, сдвиг padding и eviction из окна. Reference каждый раз строит все состояния по текущему окну с теми же позициями, mask и весами. Causal mask сама по себе не гарантирует эквивалентности. Фиксируем precision и численные допуски до сравнения. После проверки корректности измеряем стоимость update, invalidation и память; approximate reuse обозначаем отдельно. Основная серия refresh-политик работает и с полным пересчётом.

## Исходный ID-only протокол первого этапа

- Источник: официальный `yandex/yambda`, `flat/50m/multi_event.parquet`; revision, размер и SHA-256 закреплены в [конфигурации](../configs/data/yambda50m.json). Raw остаётся неизменным и не попадает в Git.
- Начальная задача: next-positive-listen prediction. История содержит **все прослушивания**, включая короткие; target — прослушивание с `played_ratio_pct > 50`. Значения выше 100 допустимы. Likes/dislikes и их отмены сохраняются в raw, но пока не входят в модель. Это явное решение нашего протокола.
- Сохраняем относительное время в **секундах**, кратное 5; это не Unix time и не число пятиминутных/пятисекундных индексов. Календарные даты не восстанавливаем.
- Последние 42 дня от конца общего диапазона: `model_valid` — 7 дней, `controller_train` — 14, `policy_valid` — 7, `test` — 14. Всё ранее — `train`. Интервалы полуоткрытые `[start, end)`, одинаковы для всех пользователей и пилота. Это наш рабочий протокол, а не воспроизведение benchmark статьи с одним тестовым днём.
- `model_valid` служит выбору checkpoint/гиперпараметров рекомендателя; после этого его веса фиксируются. `controller_train` служит обучению контроллера, `policy_valid` — настройке политик, `test` — финальной оценке. Ни словарь, ни обучающие частоты не расширяются по holdout.
- Словарь треков строится только по train-прослушиваниям выбранных пользователей: `0 = PAD`, `1 = UNK`, известные треки начинаются с `2`. Полный словарь train — общий каталог кандидатов для всех политик; повторные прослушивания допустимы.
- Неизвестные holdout items сохраняются как `UNK` в истории, но исключаются из целей ранжирования; доля исключений публикуется. Eligibility target требует известного трека, положительного прослушивания и хотя бы одного события со строго меньшим timestamp.
- События одного пользователя с одинаковым timestamp образуют группу: все предсказания группы выполняются до добавления любого её события в историю. Положительные события такой группы оцениваются по отдельности с общей прошлой историей. Стабильный `event_id` отражает строку raw, но не восстанавливает неизвестный порядок внутри 5 секунд; для уже прошлых групп это лишь воспроизводимый порядок кодирования. Учебные next-item примеры также обязаны соблюдать строгий `< timestamp`.
- История не сбрасывается на границах split. Ранее наблюдённые holdout-события разрешены как история последующих предсказаний; обновлять веса рекомендателя по ним нельзя. Текущее `played_ratio_pct` — label/outcome, а не вход текущего предсказания.
- Выбор пользователей использует только их train-историю: минимум 20 прослушиваний, затем стабильный SHA-256 от seed и uid. Пилот: 256 пользователей с полными доступными историями; основной подготовленный набор — все пользователи, прошедшие этот train-only фильтр. Различия каталогов пилота и полного набора явно фиксируются; результаты пилота не выдаются за полный Yambda-50M.
- Источник уже содержит отбор пользователей авторами датасета; наш протокол не устраняет эту исходную особенность выборки.

## Стоимость и объём работы

Подготовка ограничена 4 CPU-потоками и 4 GB памяти DuckDB, spill разрешён на локальный диск. Сначала готовим данные и измеряем пилот, затем выбираем размеры модели и число повторов. Один обученный checkpoint используется для всех основных политик. Оценка стоимости включает initialization, background refresh, recent encoder, scoring, cache handling и controller. Показываем также разбивку по компонентам. Исследовательские дополнительные fresh-предсказания не считаем deployment cost.

На первом этапе не обучаем модель и не запускаем финальные quality-метрики. Чтение диапазона/агрегатов для разбиения и аудита не является использованием test для выбора модели.
